# October 16 demo: failed media startup and stale busy reservation

Investigated October 16, 2026 using read-only Firestore outcomes, Cloud Run deployment/timing logs and Telnyx webhook delivery metadata. No caller audio or transcript was read or evaluated. Phone numbers, provider identifiers and signed URLs are omitted. The owner's reported words were not used to tune screening.

## What happened

The failure preceded either speech recognition or an AI decision. Telnyx could not establish media while the bridge was cold-starting. The API acknowledged `streaming.failed` without recovering the call. A later bridge fallback held the call executor lock while its work stalled. Telnyx exhausted all three attempts to deliver the caller's hangup and recording callback against that lock. The old reservation then refused four subsequent attempts.

All times below are October 16 **Central (CDT)**. The provider shows five inbound attempts from two distinct callers, all with a valid route to the same enrolled recipient.

## Causes and limits of the evidence

1. **Cold media startup.** Revision `shield-live-00014-pz9` had no minimum instance and was not ready before Telnyx abandoned this connection. Its database claim also preceded the WebSocket upgrade. A successful `/ready` check at release time had not exercised an idle, real-carrier connection.
2. **Missing failure recovery.** API revision `shieldapi-00020-mox` ignored `streaming.failed` and `streaming.stopped`. A provider-reported transport failure therefore received a successful acknowledgment without voicemail recovery.
3. **Cleanup competed with the executor it needed to stop.** Every callback acquired the same 25-second executor lease. The actual provider retried three times within a fraction of a second, so returning 503 did not guarantee eventual processing. Hangup proof was lost and the per-recipient busy guard remained set.
4. **Work after disconnect could be throttled.** The bridge had request-based CPU allocation (`cpuIdle: true`). The long delays after the abandoned connection are consistent with CPU throttling, but the timing logs alone do not establish the exact scheduler contribution. [Google's CPU allocation documentation](https://docs.cloud.google.com/run/docs/configuring/billing-settings) explains why cleanup outside an active request needs different execution guarantees.

The screening policy did not reject these callers. No model ran on the original call, and the subsequent attempts never reached screening. No screening prompt changes are justified by this incident.

## Implemented recovery, not deployed

- Authenticated, correctly bound stream-failure/stopped callbacks transactionally move an active screening to voicemail. Recovery works before or after bridge claim, bypasses a stuck executor, and retries the same durable provider command ID. Late callbacks cannot change offered or accepted calls.
- A confirmed hangup for an unconnected inbound leg atomically records carrier termination and releases only that call's reservation without acquiring the stalled executor. Offering/connected calls retain coordinated two-leg cleanup. A duplicate old hangup cannot release a newer call's reservation.
- Correctly bound recording callbacks persist their existing idempotent ingestion job without waiting for the executor lock.
- Outcome routing rechecks carrier termination after stopping the stream. A saved-notice decision is still explicitly hung up; an application decision marked `ended` is not confused with proof of carrier termination.
- Media stop/close/error and missing start select the safe fallback. Malformed messages and a rejected fallback are contained within the transport. A dedicated `provider_start_timeout` timing identifies this failure phase without logging content.
- The bridge deployment defaults keep one instance warm and disable idle CPU throttling. This increases standing hosting cost and still does not guarantee that a container can never restart; recovery remains necessary.

Recipient binding, press-1 acceptance, screening deadlines, call limits, v158 screening and deployed post-call filtering are preserved.
