# Contact change recovery — October 18, 2026

**Repository correction and frozen API package; not deployed or installed on a physical phone.** Contact edits must remain consistent when a response is lost, the app closes, access is revoked or an older refresh finishes late. The current theme is preserved. [Backend review and rollout boundary](CONTACT-RECOVERY-ROLLOUT.md).

## Reproduced failures

A harness compiled the unchanged production `SharedContactsModel` with synthetic network and Contacts actors. The positive control passed, while two independent cases failed:

1. The server saved a removal, then its response was lost. The old model restored only iPhone Contacts, leaving the phone and service in opposite states.
2. An older held refresh completed after a confirmed removal and put the contact back in the visible list.

These were local, deterministic reproductions, not real calls or changes to the owner's address book. Original source, harness and results remain under `artifacts/private/contact-recovery-oct18/`.

## Recovery contract

Before editing a native contact, the app saves one unfinished operation for that account and protected person. It includes the selected row, desired state, request ID and expected list revision. The file uses complete file protection, owner-only permissions and backup exclusion. Sign-out retains it for the same login; another account cannot read or resume it. Successful reconciliation clears it. Account deletion clears this account's records only after the server accepts deletion or confirms its receipt; rejected, unsent and uncertain deletion requests retain recovery.

Opening, refreshing or foregrounding the screen reads status only. It does not edit Contacts, request Contacts permission or upload the address book. A fresh server result can confirm completion only when the list revision has advanced, the saved row state matches the request and authorized native Contacts inspection agrees. Uncertainty remains visible and blocks competing edits in that screen. The user can check again or explicitly continue the requested edit. A deleted restoration target can be kept removed with a separate confirmation, then added anew if desired. The app never silently restores a contact just because a server response is missing.

The API returns a consistent list/revision snapshot and advertises `revision-v1`. Versioned changes atomically compare the revision, update the contact and record a receipt. Replaying the same receipt and intent does not write twice. Newer individual changes, explicit full shares and legacy mutations supersede older requests. Versioned full-share requests also compare their starting revision, preventing an older delayed upload from overriding a newer edit. Reads and individual changes reject an active full-share lease instead of treating a partial batch as confirmed.

The app requires this contract before sharing or changing native contacts. Earlier clients remain wire compatible, but retain their earlier client-side recovery limitations. **Deploy and verify the API before distributing the updated app.** No new entitlement, caretaker access, automatic sharing, call-control behavior or delivery activation is included. Removed server rows remain disabled/restorable under the existing contact-retention policy; this is not a new server erasure promise.
