# iPhone contact number identity

## Confirmed defect — October 18

The API normalizes shared phone numbers with the pinned `libphonenumber-js` parser. The iPhone previously compared only extracted digits. In an authorized iOS 26.5 Contacts test, eight of eleven accepted formats were not recognized and removal returned success while the original field remained. The app also reported those numbers absent afterward. The failing formats cover four extension notations, Arabic-Indic and fullwidth digits, an international dialing prefix and an international trunk prefix. Three ordinary formats passed. These were temporary synthetic cards, not real calls or customer contacts.

## Local correction

The iPhone now bundles the exact existing `libphonenumber-js` 1.13.13 browser parser used by the deployed API candidate, with its MIT license and hash manifest. JavaScriptCore runs it offline inside `PhoneContacts`' serialized access; the app exports no device or network API to the script. Apple's [JavaScriptCore threading documentation](https://developer.apple.com/documentation/javascriptcore/jsvirtualmachine) supports this serialized use across actor executor threads. The bundle is fixed at build time; there is no downloaded executable code or new package version.

Native lookup scans authorized Contacts with the server's number identity because the native phone predicate is insufficient for the accepted formats. An invalid field is ignored consistently with the server. Parser failures throw an error rather than confirming absence. Manual entry and explicit address-book sharing retain their existing behavior. Passive recovery still requires existing full permission and does not request permission, upload contacts or edit them.

Removal saves a protected local backup before changing matching phone fields. Removing a number that is already absent creates no empty backup. Restoration keeps original values, labels, distinct extensions and duplicate-field counts. If an original card was deleted, it recreates its saved phone fields and names and reuses an already restored copy on retries. Only a missing-record error permits that fallback; other Contacts read errors propagate. Unrelated fields on surviving cards remain unchanged. The app does not back up or recreate a deleted card's unrelated email or other data. After reading back every restored phone field, it consumes that number's backup. A later account deletion therefore cannot resurrect contacts deliberately deleted after restoration. Legacy empty entries are ignored by Restore All.

The normal repository checks compare the bundled parser and license with the installed pinned dependency. The release-archive check verifies their actual archived bytes and rejects the new simulator fixture markers in the production binary.

## Verification checkpoint

- Actual Swift parser/Contacts source compiles. Eleven identities match the actual backend, five invalid inputs are rejected, and six deliberately broken parser cases fail safely. Four extension cases retain extension information. A 5,000-parse measurement took about 266 ms on this Mac; it excludes Contacts enumeration, iCloud and device work.
- The initial clean iOS 26.5 candidate passes three native methods and 192 assertions across sixteen scenarios. A further lifecycle regression then reproduces **64 failures**: an empty backup for an absent number, a retained backup after each restore, and recreation of deliberately deleted fixture cards. After the correction, all **256 assertions across sixteen scenarios** pass, along with the existing sharing/restoration methods and corrected Disconnect route. Cases include distinct extensions, alternate formats of one number, identical duplicate fields, a deleted card and multiple cards. Every temporary card and local restore copy is removed by the fixture.
- The final combined iOS 26.5 run passes **nine methods**, with the iOS 27-only VoiceOver method skipped: three Contacts methods, four interrupted-change recovery methods and both corrected navigation routes. Its source inputs are unchanged through the run. The matching iOS 27 run passes **ten methods**, including its VoiceOver recovery method, with the same recorded source inputs. Both runtimes pass all 256 scenario assertions.
- The final unsigned Release archive passes all archive checks with **248 recorded production inputs unchanged**. The actual archived parser and license match, and the new simulator fixtures are absent from the release binary. This is not distribution signing or Apple acceptance.
- Local repository checks pass typecheck/build and **394 unit tests**. The unchanged database suite passes **293 tests**, using isolated emulator ports to preserve the existing emulator.
- First-attempt [independent CI on committed checkpoint `bd1d5ca`](https://github.com/tigerisaac/aaacap-project/actions/runs/39175922622) passes typecheck/build, the production dependency audit and **394 unit + 293 database + 12 account checks**. These backend checks do not replace native app, device or Apple acceptance.

The first native diagnostic had a label-symbol compile error, then stopped on missing Contacts permission. The authorized baseline established the actual defect. An early candidate compile found a Swift isolation error; parsing was moved out of the native enumeration callback. Two candidate runs produced all sixteen successful scenario reports but incorrectly asserted an older eleven-case expectation. The built and installed test binaries matched. A clean rebuild of unchanged source passes; the earlier failures remain retained and their underlying cause is unproven. The first local repository run could not bind its loopback test servers in the sandbox; the authorized run passes. The first unsigned archive failed because the local volume ran out of space, with no source-input changes. Only verified task compiler/index caches and an unused task-created simulator were removed; results, app products, source and rollback packages were preserved. The final two-job archive passes. The isolated iOS 27 counterpart subsequently passed all ten methods. Its temporary simulator was removed after retaining the reports; other simulators were preserved.

The separate full iOS 27 suite is still running against its frozen pre-correction app and test products. Its 56 product hashes remain unchanged. Its Disconnect test fails to scroll to the Account row, and its forwarding test expects an always-visible recovery action to be hidden. Both reproduce with a clean iOS 26.5 candidate; test corrections preserve the user-facing behavior. The forwarding test passes after checking the recovery action stays available; the Disconnect test passes after scrolling, allowing lazy rows to appear before reading their frames, and matching the combined title/detail accessibility label. Its capture was inspected: the destination and primary content are correct; the narrow native navigation title is ellipsized while the full page heading remains visible. These results are not yet a final all-app pass.

Four focused captures were inspected. The forwarding recovery action is visible and the Disconnect destination is correct. At maximum text, however, the contact recovery action splits the word “Check” across lines and the native search field overlaps the scrolled content. Reachability checks do not establish readable wrapping. These observations remain part of the open accessibility review. ## Release boundary

This is an iPhone source correction; no backend deployment, sharing permission, caretaker scope, live call, carrier setting or delivery activation changed. Physical Contacts—including limited/read-only sources, iCloud and large restore operations—still need device acceptance. Real routing after removal/restoration, complete accessibility, Apple signing/distribution and the other [public/pilot release gates](APP-STORE-RELEASE.md) remain open.
