The earlier [contact-consistency audit](SCREENING-CONTACT-CONSISTENCY-AUDIT.md) supplies the development baseline. ## Changes grounded in development

The v145 billing miss states an unnamed service role and describes its ordinary bill in the established customer account. Both trials ask questions; both mark identity missing. V143's shortening had removed the explicit business-type wording. V146 restores that distinction in the identity instructions and field description. This is a plausible contributor, not proof of the entire cause.

V146 also reports a conflicting identity/context pair together. Opt-in correction version 3 asks the model to recheck both and correct whichever is unsupported. It never reflects rejected values, unknown property names or free-form schema errors. Earlier correction versions remain unchanged. An independently decisive charge alarm or prohibited request still blocks before relationship correction.

V146 development exposes the remaining billing problem: one trial now identifies the role and ordinary financial update correctly, but still marks context missing and asks for an action. V147 lets an observed ordinary financial update supply otherwise-missing context. It does not override substantive unresolved claims or promotion, invent identity, weaken charge/restricted-conduct priority, or change recorded-notice, trusted-caution, evidence or unanswered-question guards. Original observations remain in the audit trail. No new initial wording is added.

The v146/v147 initial requests are identical: 4,333 instruction characters plus 5,599 tool characters, totaling 9,932. This is 21 characters above v145 and 17.7% below runtime's 12,069. Character counts are not token or cost measurements. Their request hash is `116164705408ef3ffe8bc923b724d494403ae2ddcbbf073f9ad15518247a85f1`.

## What the failures mean

V146's joint correction is not a semantic guarantee. In three development trials it resolves the formal inconsistency in one retry but the resulting missing context still loses an ordinary offer. The model can supply consistent but wrong facts. A cousin's invitation to share family pictures and a neighbor's warning against computer commands are legitimate under the intended policy; their misses are not excused as benchmark defects. Endorsing another caller's offer to control the recipient's computer is a restricted request and should stop.

The social checking-in case is more nuanced: it states a name, previous contact and a social purpose, but does not explicitly say friend. A relationship question is cautious, yet loses the original ordinary-offer expectation. Its original label and score remain intact. The two historical SSA saved-message expectations also remain in strict development scores; blocking those source-scam threats is not an ordinary-caller false block.

Deterministic replay of the saved v146 development observations through v147 changes one billing trial from continue to approve; replay of all v146 MASC observations changes no action. The new v147 billing trials both approve, but both already report ordinary context, so those two successes do not exercise the new fallback. This is diagnosis, not replacement score credit. The application audit finds no changed action from the new fallback anywhere in the actual v147 runs; two fresh missing-identity observations change only decision metadata while retaining continue. Thus the observed public and development score differences between these identical initial requests are sampling differences, not measured gains from the fallback.
