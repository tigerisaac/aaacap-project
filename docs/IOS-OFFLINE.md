# Local history and recordings

## Navigation caching — October 16, repository implementation

Owner call lists, message lists, call details and overview responses now share a bounded, session-local cache for 60 seconds. Trusted, saved and blocked numbers reuse responses for five minutes; public configuration lasts an hour. Keys include the participant and complete path (including filters and pagination). Only people freshly identified as owners by `/api/people` qualify; helper reads still check server access. Concurrent reads share one request. The cache holds at most 128 responses and 8 MB, with a 1 MB per-response limit.

Home, its setup checklist and onboarding reuse confirmed owner configuration for up to five minutes, including its protected saved copy and original check time. Home renders the saved setting before any network wait. A failed refresh retains that setting with its confirmation time; a copy older than a day asks for reconfirmation. Temporary windows still expire locally, and known paused/disconnecting states override an enabled snapshot. This is configuration presentation, not live service or carrier-forwarding proof. Setup actions still read current status directly. Pull-to-refresh, incoming audio-delivery notifications and mutations invalidate navigation data; ordinary foreground and periodic refreshes honor cache lifetimes, and public configuration survives ordinary refreshes. Sign-in, sign-out and authorization failures clear the whole cache. Invalidated in-flight requests cannot refill it, even if their transport finishes late. Failures are not cached.

Message pages now also save their summaries to the existing protected owner history, including older pages browsed in Messages. History/audio persistence remains separate from the session-only response cache; saved-number responses are not persisted across app launches.

Navigation presentation retains loaded empty call filters and the current owner inbox while refreshing. Calls uses compact toolbar progress only for a first load without content, after 250 ms; fast cache reads never insert a loading card. Local Calls filters match the server’s outcome query, including Messages: stopped calls with removed-message metadata stay in Stopped. Filter selection updates the displayed rows synchronously, before the request task runs. The delay belongs to the stable screen rather than an empty List section, so genuinely slow loads still display progress. The Messages page no longer shows the permanent audio-storage/delivery disclaimer. Actual delivery errors remain visible when they occur.

This review found that the earlier device/Release playback branch still called the remote audio endpoint, while the debug simulator branch used the local library. Playback now has one common local-first path on both devices and simulators. Already-delivered owner audio plays from the verified local file; only missing audio needs delivery. The existing server acknowledgement/deletion contract is unchanged. This correction supersedes the earlier unverified claim that the installed physical-device UI played saved audio locally.

Validation and installation status are recorded in [Status](STATUS.md). The signed update was installed on the paired iPhone 12 Pro Max at the owner’s request on October 16 at 23:51 Central. No cloud deployment is required for these client changes; physical airplane-mode playback still needs verification.

The iPhone app previously kept most call history only in memory. Reopening it required `/api/people`, public configuration, setup/contact checks and history requests before its normal screens had data. A temporary connection failure could therefore look like an unusable app, even though cloud call screening continued independently.

The October 16 update loads the signed-in owner's protected local history before refreshing the service. It retains up to 500 previously loaded calls per owner, removes history older than 30 days, and supports Home, call filters and call details without a successful request. Message summaries in this history are available before the recording arrives. Saved audio has its separate durable library and plays locally. Newly loaded calls appear before optional setup/contact/notification checks finish; overlapping full refreshes are coalesced.

The history is account-scoped, atomically written, protected with iOS Data Protection, and excluded from backups. Helpers' shared history is not persisted: fresh access is required because sharing can be revoked. Sign-out hides local data, account deletion removes it, and confirmed message deletion removes the corresponding history copy. Transient token-refresh failures retain the session; explicit authentication failures still require sign-in.

Home keeps its last confirmed configuration and saved counts visible during refresh or a failed update, without inserting a timestamp line. It retains confirmation times internally and asks for reconfirmation after a day. It does not treat network failure or a 75-second-old response as evidence that checking stopped. Cached configuration is never proof of current cloud health or carrier forwarding. Calls and Home do not insert storage-timestamp banners during navigation. Initial sign-in, new calls/messages, shared access, account/settings changes and server-side message deletion require a connection. Live screening needs the cloud services and carrier connection, but the iPhone app does not need to remain open or maintain a continuous server connection.

## Evidence

- Swift storage tests cover restart, account isolation, backup exclusion, 30-day expiry, stale-account writes, deletion and corrupt files, alongside durable audio delivery/failure tests.
- The real AppState/Calls/detail views passed a simulator cold-launch/relaunch/filter/detail test with an in-memory synthetic identity and an unavailable API. No real credentials or network service were used. The first attempt targeted a Home button below the lazy list's visible area; the corrected test uses the visible Calls tab and passed.
- The separate audio simulator test passed playback before and after app restart, with backup exclusion checked.
- A signed build was installed and launched on the owner's paired iPhone 12 Pro Max on October 16. No carrier settings were changed and no phone call was placed. Physical-device airplane-mode, background delivery timing and hardware encryption were not directly tested.

## Phone setup and disconnect instructions — October 17

Owner setup responses and the approved carrier restoration text are now saved in an account- and participant-scoped Application Support cache, excluded from backups and protected until the first device unlock. The cache is limited to setup/forwarding presentation data; it never stores a completed restoration as proof that service is off. Account deletion clears it, refreshed owner lists prune removed profiles, and session/generation checks prevent old requests from writing after invalidation.

Home refresh warms Phone setup automatically. Phone setup immediately displays its saved response, reuses it for five minutes, and refreshes stale information while retaining the form. Writes and explicit refresh invalidate freshness without throwing away readable instructions. A saved timestamp distinguishes the displayed state from a live service check. Delete account remains in account settings and is removed from both Phone setup variants.

Disconnect opens its bundled instructions and saved carrier text without a server request. “Read all phone steps” works offline; no carrier code is inferred from the carrier name. Starting or resuming the guided workflow first reads the restoration protocol, then uses explicit server-confirmed transitions. This prevents an older deployed `/restore` handler from being called as a fallback. Network failure cannot advance progress or claim that Shield service has stopped. Ordinary and trial setup now link to the same guide.

Live call handling, authoritative account/routing changes, and new message delivery remain server responsibilities. Saved guides, already received audio, and cached presentation data remain readable locally. This change does not establish real-call or carrier-restoration verification.
